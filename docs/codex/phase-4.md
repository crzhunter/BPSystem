# 第四阶段 · 录像分析

首页继续打开实时 BP 对局室。比赛库里的「查看热力图」链接指向 `/#replays?matchId=比赛编号`，刷新或分享给同一服务器的其他设备会保留单场范围。桌面侧栏提供全部入口。手机底栏依次为对局室、战队、选手、比赛库和录像分析，设置入口位于顶栏。

实时 BP 对局室的「对手情报卡」可直达「对手眼位热图」或「对手核心刷钱」，并预选敌方阵营。有战队预设时汇总该队。手选阵容时，眼位优先取 4–5 号位，刷钱优先取 1–3 号位。对应位置空缺时取首位已选对手，阵容为空时只按阵营筛选。

## 从请求解析到回填

1. 比赛库和录像页的待解析清单都能提交 `POST /api/matches/:matchId/request-parse`。本地已解析时立即返回 `already_parsed`。其余场次向 OpenDota 提交，提取返回的 `job.jobId`。
2. 浏览器在当前标签页的 sessionStorage 中按比赛保存任务编号，随即查询状态。任务仍在队列时，等上次查询结束后再等 5 秒。切页会取消计时，重新显示这场待解析比赛或刷新页面后会继续。临时断网时「继续查询」复用已有任务。
3. 状态接口读取上游 `GET /request/{jobId}`。返回 `null` 或明确完成时，绕过本机一小时的旧比赛缓存，重新请求 `GET /matches/{matchId}`。返回失败状态时结束轮询。如果任务提供了比赛编号，服务端会校验归属。
4. 复用比赛导入事务，验证比赛 ID、十个唯一槽位和双方阵营，写入选手、禁选、眼位及分路坐标。沿用赛事标签。解析标志、解析版本号或实际眼位／坐标可以确认已解析。任务出队后若上游仍没有解析数据，会得到 `failed`，页面可再次请求。事务失败时保留原记分板。查询期间已删除的比赛不会被重新创建。

两种上游任务请求都跳过 SQLite 响应缓存，沿用设置页密钥与滑动窗口限流。同一客户端合并同时发出的相同请求。提交任务按十次调用预留额度。GET 可重试 429 和临时服务错误，POST 仅对明确的限流响应重试。[OpenDota 请求接口实现](https://github.com/odota/core/blob/master/svc/api/spec.ts)

## 坐标与统计口径

以原始列为 x、行为 y。数据库中的 `lane_pos_json` 如 `{"120":{"110":5}}` 表示格点 (120,110) 累积权重 5，序列化后的数字键按数值读取。横轴向右、纵轴向下。

```text
nx = clamp((x - 64) / 128, 0, 1)
ny = clamp(1 - (y - 64) / 128, 0, 1)
```

| 原始坐标 | 画布坐标 | 位置 |
| --- | --- | --- |
| (64,64) | (0,1) | 左下，天辉 |
| (128,128) | (0.5,0.5) | 中心 |
| (192,192) | (1,0) | 右上，夜魇 |

越界值钳制到图边，响应保留原始值。缺少有效坐标或时间的眼位跳过。全场包含开战前的负时间。对线期、中期和后期分别取 `[0,600)`、`[600,1500)`、`[1500,+∞)` 秒。眼位统计量与图上可定位的事件一致；比赛详情中的守卫计数包含原始日志中缺坐标的记录。

按战队聚合时，用本地预设当前首发及替补的账号匹配历史参赛者；按选手时传选手库主键。队友每场分别按实际阵营计数。玩家位置和眼位查询均支持按赛事标签精确过滤。眼位样本场次先按人员、阵营、比赛和标签筛选，再区分已解析和待解析。时间和眼位类型只筛选事件。

眼位热点把归一化坐标划入 8 × 8 网格，按事件数取前五格，地图坐标为该格内事件的质心。核心筛选采用约定的分路代理值 `lane_role=1..3`，缺失时复用英雄的 `typicalRoles`。每名选手每场至少有一个有效正权重格点才计为一个样本人次。GPM 和 XPM 分别对有值的人次求算术平均，零值有效。热度单元按相同原始 x、y 累加，强度为单元权重除以当前峰值。

区域占比为该区位置权重除以所有入选位置的总权重。按顺序将每个样本归入首个命中的区域，得到六个互斥的近似区域。

| 区域 | 归一化坐标判定 |
| --- | --- |
| 中路 | `abs(nx + ny − 1) ≤ 0.085` |
| 河道与肉山周边 | `abs(nx − ny) ≤ 0.09` |
| 上路/优势路 | `nx < 0.16` 或 `ny < 0.16` |
| 下路 | `nx > 0.84` 或 `ny > 0.84` |
| 天辉野区、夜魇野区 | 剩余位置按 `ny > nx` 归天辉，其余归夜魇 |

侧栏显示每区一位小数，四舍五入可能令显示合计相差 0.1 个百分点。分路采样只反映上游记录到的位置密度，无法重建逐秒移动路线或计算各野区实际获取的金钱。

## 适配器与画布

`server/src/services/replayAdapter.ts` 定义 `ReplayParserAdapter.parseReplay(matchId, slots, layer)`。输出一组以实际 `playerSlot` 标识的轨迹。每条包含 `obs`、`sen` 的 `{x,y,time}` 事件和 `positions` 的 `{x,y,weight}` 样本。时间单位为秒，原点保持游戏坐标系。允许同步结果或 Promise。默认适配器按比赛与槽位索引从 SQLite 只读取当前图层的列。聚合层负责人员、角色、时间过滤与坐标转换。

将来接入离线解析器时，可由适配器按比赛 ID 定位本地录像，调用独立进程并翻译成上述数据，在 `createApp` 第五个参数注入实例。比赛库仍提供槽位及参赛者身份，应先准备对应已解析比赛的元数据。当前交付使用 OpenDota，运行时仅依赖 Node 24 内置 `node:sqlite` 访问数据库。

底图与补丁来源见[五期数据说明](./phase-5-bp-overhaul.md)。历史场次共用当前底图，跨版本复盘时请留意地形差异。

热力层先合并像素格，再由 Canvas 径向渐变生成高斯核，以浮点数累加样本密度，按当前视图的峰值映射为蓝、绿、琥珀和红色。调整不透明度仅改变图层合成。精确标记使用独立的高分屏画布。金色圆环代表假眼，青色菱形代表真眼。悬停或点按显示时间、英雄、选手、阵营与比赛 ID，重复点按可切换重叠事件，键盘左右键也可逐个查看。

## PWA 和验证入口

生产构建把应用根页、脚本、样式、清单、图标和整个随包美术目录写入 Service Worker 预缓存。缓存版本包含资源路径、静态资源内容及 Worker 模板。清单启动地址为 `/`，深链接沿用同一个页面外壳。通过 HTTPS 或 localhost 在线打开并完成安装后，离线刷新可打开录像界面和地图；筛选、解析和比赛数据读取需要连接服务器。普通局域网 HTTP 可直接使用移动网页。

运行 `npm run typecheck`、`npm test`、`npm run build`。第四阶段回归位于 `server/test/phase4.test.ts`，通过临时 HTTP 服务、内存 SQLite、模拟 OpenDota 和可替换适配器检查筛选边界及真实入库结果。接口清单见 [REST API 参考](api.md)。

本次在 Windows、Node 24.15.0 下三条命令均以 0 退出，全库 45 项测试通过，其中四期 9 项。以下操作在 Edge 中使用生产构建实测。

- 桌面从比赛库进入指定比赛，检查眼位悬停信息、标记开关和时段筛选。
- 375px 视口逐项进入五个底栏页面和顶栏设置页，页面宽度均为 375px。触摸输入可点选眼位，打钱视图显示六项区域占比。
- 通过模拟 OpenDota 排队，切页并刷新后继续查询，只提交一次任务。完成后待解析比赛移出清单，眼位计数随回填更新。
- 首次联网完成预缓存后断网，直接打开并刷新录像深链接，方形地图正常显示，数据接口进入可重试的离线状态。

移动验收使用桌面浏览器的触摸模拟。公网真实排队等待时间和实体手机安装体验未实测。
