# 第三阶段 · 实时 BP 对局室

## 队长模式与对局进度

打开首页即可开始一场 7.3x 队长模式禁选。服务端与页面共用 `server/src/data/cmOrder.ts`。F 是先选队，S 是后选队，天辉和夜魇都可以先选。我方阵营只决定推荐视角。

| 阶段 | 步号 | 动作 | 顺序 |
| --- | --- | --- | --- |
| 第一阶段 | 1–7 | 禁用 | F S S F S S F |
| 第一阶段 | 8–9 | 选取 | F S |
| 第二阶段 | 10–12 | 禁用 | F F S |
| 第二阶段 | 13–18 | 选取 | S F F S S F |
| 第三阶段 | 19–22 | 禁用 | F S S F |
| 第三阶段 | 23–24 | 选取 | F S |

每队禁 7 名、选 5 名，共 24 步。完成后 `currentStep.step` 停在 24，`isCompleted` 为 true，`isOurTurn` 为 false。撤销最后一步即可恢复禁选。

## 存储与接口

SQLite 由 Node 24 内置的 `DatabaseSync` 打开。迁移 v3 在 `draft_sessions` 加入双方各五个选手槽位和整数修订号，在 `hero_matchups` 加入反向查询索引。槽位按 1–5 号位排列，记录本地选手 ID，空位为 null。战队预设此后换人不会改写已保存的阵容。删除选手会释放其位置，动作保留英雄和已有位置提示。三期 JSON 备份包含存档、动作和对位，仍可恢复二期备份。二期没有记录的阵容位置以空位读入。

下表路径统一以 `/api` 开头。

| 方法和路径 | 用途 |
| --- | --- |
| GET /bp/sessions | 按最近更新时间倒序列出存档，包含标题、修订号、状态和已执行步数。 |
| POST /bp/sessions | 创建并返回完整存档，HTTP 201。接受 title、notes、patch、ourSide、firstPickSide、radiantTeamId、direTeamId、radiantPlayerIds、direPlayerIds。可带 actions，将已进行的草稿一次保存。 |
| GET /bp/sessions/:id | 返回上述元数据、十个选手位置、actions、带已执行动作的 24 格 timeline，以及 currentStep。 |
| PUT /bp/sessions/:id | 部分更新元数据和阵容。传 actions 可整体保存草稿。修改先选权时重新计算历史阵营，已有选手归属须仍与阵容相符。 |
| POST /bp/sessions/:id/action | 传 heroId 执行下一步。可传 stepIndex（或 step）指明当前步，或用不同的英雄修正已执行的一步。可选 assignedPlayerId 和 roleHint 仅用于选人。 |
| POST /bp/sessions/:id/undo | 撤销最后一个动作，返回更新后的对局。 |
| POST /bp/sessions/:id/reset | 清空动作，保留战队、槽位、先选权和备注。 |
| DELETE /bp/sessions/:id | 删除该局及其动作，成功返回 204。 |
| POST /bp/recommend | 传 sessionId 读取存档，或直接传草稿状态，返回当前步、两张推荐榜、阵容体检和情报卡。 |
| POST /heroes/matchups/sync | 传 heroIds 数组，仅同步指定英雄。空数组不发起请求，省略 heroIds 则同步全库。返回 requested、synced 及逐英雄结果。 |
| GET /heroes | 英雄资料增加 typicalRoles 和 tags，供位置筛选和战术分析使用。 |

未保存草稿的推荐请求示例，省略的位置自动补为空位。

```json
{
  "ourSide": "dire",
  "firstPickSide": "radiant",
  "radiantPlayerIds": [],
  "direPlayerIds": [],
  "actions": [{"heroId": 1}, {"heroId": 2}]
}
```

下一步为夜魇第 3 步禁人。服务器从顺序表推导动作与阵营。重复英雄、越步、选手在双方重复上场、同队重复分配选手或位置均返回 400。写入在同一事务内校验，失败时保留此前的对局。更新、执行、撤销和重置可携带读取时的 `revision`。修订号过期返回 409，界面可重新载入或另存为新对局。存档不存在返回 404。

## 推荐评分

`bpEngine.ts` 在本地读取英雄资料、双方英雄池、已选英雄对位和赛事组合。每局返回最多 10 条禁人、10 条选人建议，排除双方已经使用的英雄。我方五人选齐后收起选人榜，整局完成后收起两榜。得分限定为 0–100，保留两位小数，同分时按英雄 ID 排序。分数用于比较候选优先级。胜率、场次和胜负记录另行展示。

### 共同输入

- **选手熟练度 H** 直接取二期 `analytics().heroPool[].weightedScore`。赛事权重、近期窗口、赛事与路人去重、小样本平滑均沿用二期实现。
- **阵营修正 B** 为 `10 × (胜场 − 场次 / 2) / (场次 + 4)`。仅统计该选手用该英雄在本场阵营的已知逐场记录，空样本贡献 0。
- **对位优势 D** 对每个已亮英雄计算 `(胜场 − 场次 / 2) / (场次 + 10)`。优先使用候选对已亮英雄的记录，仅有反向记录时取其相反数。空样本取 0。多目标时，D 是所有目标平均值与最强正优势（最低取 0）的平均值。禁人榜在第二、三阶段对我方已亮的 1–3 号位额外乘 1.3。
- **战术资料** 由 `heroTags.ts` 提供常见位置、硬控、先手、推进、爆发、团战、救人、摇摆、前排和线优标签。常见位置保留优先次序。新同步的英雄可以使用 OpenDota 职责回退。已有英雄的硬控按技能单独标记。

### 禁人榜

以 `H + B` 排在首位的敌方使用者作为主要威胁来源，基础分为 `0.74 × H + B`。第一阶段的 S 级招牌英雄（H ≥ 70），敌方先选加 10，后选加 7。至少两名敌方选手达到熟练门槛时，第一阶段按敌方先选或后选加 11 或 9，后两阶段加 5。对位项第一阶段加 `22 × D`，后两阶段加 `60 × D`。理由指出位置、赛事或路人战绩、可摇摆的位置、受威胁的我方英雄。没有个人或对位样本时，威胁分可以为 0。

### 选人榜与体检

体检先锁定手动指定的位置或选手槽位，再把未分配的英雄匹配到各自常见位置，尽可能覆盖五个不同位置。一个摇摆英雄只计一个位置。输出 `coveredRoles`、`missingRoles`、各标签数量和具体缺口。

对每个候选英雄分别评估未覆盖的位置，建议分最高的位置和未分配选手。已指定跨位置选手时，原位置上的队友可补到空位。空槽仍可建议位置，`suggestedPlayerId` 为 null。

| 分项 | 分值 |
| --- | --- |
| 个人英雄池和阵营 | 0.53 × H + B |
| 位置 | 常见位置符合缺口加 12，第一常见位置再加 2 |
| 职能缺口 | 硬控、先手、拆塔、救人每补齐一项加 5，最多 14 |
| 配合 | 首次补入可衔接现有先手的团战英雄，或首次为已有前排补入救人英雄，加 5 |
| 首轮稳定性 | 可摇摆、有前排能力或线优的英雄，我方先选加 8，后选加 5 |
| 对位 | 第一阶段 24 × D；后续通常为 56 × D；第三阶段我方后选为 68 × D |

## 对手情报与对位同步

优先禁用榜列出最多五名有敌方实战记录的可用英雄，分别显示主要使用者、赛事记录、路人记录和威胁分。摇摆位预警要求至少两名敌方选手各自达到 H ≥ 45，且各有至少 2 场赛事或 5 场路人样本。

组合从已导入且有胜负的赛事中，按账号匹配当前敌方名单，按比赛 ID 和实际阵营分组。同一场站在不同阵营的选手不能构成组合。对同侧英雄枚举二人组和三人组，记录场次与胜场，按场次、胜场排序，每种规模最多显示三组。单次同台也会显示 1 场。阵营表现采用选手出场人次汇总双方胜率，范围包含赛事和已知阵营的路人逐场。五人同场计五人次，胜率由总胜场除以总人次计算。无样本显示「—」。

同步使用一期 OpenDota 客户端逐个请求 `GET /heroes/{hero_id}/matchups`，复用滑动限流、重试、同请求合并与一小时请求缓存。以英雄对为键更新场次、胜场及时间。每个英雄单独提交事务，一批数据损坏时该英雄整批回滚。遇到上游错误时停止后续抓取，返回已成功数量和失败原因，之前缓存仍可用于本地推荐。页面的同步按钮仅提交本局已经选取的英雄；从反向胜率即可评估尚未选取的候选。

推荐请求不访问外网。服务按当前十人名单、我方阵营和数据库变更标记复用最近一次英雄池与组合统计，每分钟重新评估时间窗口。对位查询使用已选英雄和双向索引。没有对位矩阵时仍返回位置、职能和英雄池建议。

## 桌面与移动操作

- **桌面**在 1024px 起使用三栏。左侧天辉，右侧夜魇，中间显示当前步并选英雄。阵容体检和选人推荐跟随我方，禁人榜和情报卡跟随敌方。按中文名、英文名或简称搜索，可叠加主属性及位置过滤。选人前可指定位置，已填槽位同时记录选手，亦可先选英雄、暂不分配。
- **移动**在 768px 以下显示吸顶步号、当前行动方和撤销按钮。使用「BP 进度」「智能推荐」「对手情报」「选择英雄」切换内容，展开「对局配置与存档」可改阵营、同步、重做、重置或载入存档。
- **保存**时可填写对局名称、比赛版本和备注。当前草稿自动保存在浏览器，重开同一地址可继续。更新服务器存档后，其他设备可从存档列表载入。撤销后可以重做，执行新的禁选动作会清空重做记录。已进行的对局可以整体交换阵营，同时保留队伍身份、先选权和选手归属。

## 验证

根目录运行 `npm run typecheck`、`npm test`、`npm run build`。三期测试位于 `server/test/phase3.test.ts`。耗时用例包含 10 名选手、127 名英雄、1,270 条个人英雄池记录及 16,002 条有向对位，预热后连续测量本地推荐。测试诊断会输出实际耗时。

在 Windows Edge 的 1024px、1440px 视口检查了三栏排列，并从首页操作到第 24 步。在 375 × 812 视口操作四个子页、吸顶撤销、重做、存档和重置，检查了页面宽度及浏览器脚本异常。浏览器验收使用独立内存数据库。另用真实 OpenDota 接口同步敌法师，得到 126 条对位记录。
